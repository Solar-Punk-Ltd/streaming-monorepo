# The web2 admin link

The web2 admin (the admin) is a separate service where streams are declared and
listed. A deployment's stream uploader reports to it when the stack gives it
`ADMIN_API_URL` and `ADMIN_API_TOKEN`. The web2 admin link is how the manager sets
that up: one link for the whole manager, which every new uploader deployment
starts with, and a token of its own for every uploader linked to it. This is a
feature page of the manager, the web console and API in `apps/infra-manager` that
deploys the streaming stack (`apps/hls-stream`) onto hosts.

The same link is where the manager pushes each stage's record and the catalogue
stamp record ([stages.md](stages.md)). The operator's view of the routes is the
section [Linking uploaders to the web2 admin](../../manager/README.md#linking-uploaders-to-the-web2-admin)
of the API reference.

## What it does

- **The manager's link.** An admin address and a token, saved once on the
  **Manager settings** page. A new deployment that runs a stream uploader starts
  with the link's address.
- **The registrar token.** The token the link stores. It is the admin's
  `INTERNAL_API_TOKEN`, which registers stages. Only the manager presents it, on
  its pushes and on Test connection. No deployment is given it.
- **A token of its own.** The `ADMIN_API_TOKEN` the manager generates for each
  uploader linked to its admin. The admin learns it from the stage record, by its
  sha256, and takes no other token from an uploader.
- **Origin.** The scheme, host and port of an address. A stored token goes only
  to the origin it was stored for.

## The two keys, and the rule they answer to together

Both keys are typed fields in `common/src/stackSettingFields.ts`, so the page and
the manager hold a value to the same rule before any save. The address is an http
or https address with a host and no user name, password or `#` part, because the
uploader builds every request by adding a path after it. The token is at least
`ADMIN_API_TOKEN_MIN_LENGTH` (32) characters, the floor the uploader itself
holds. No refusal repeats either value.

The uploader turns admin mode on from the address alone, and then refuses to
start without a token. So `adminLinkEditProblem` in `common/src/adminLink.ts`
works out what the two keys come to once a save or a create lands, and refuses an
address with no token anywhere, naming both keys. A token counts wherever it
comes from: stored for the deployment, set by the version, or generated by the
manager. The manager reads those server side, where the secrets are. A token of
the deployment's own counts only for an address on the origin of the manager's
link, since that is the one address a deploy writes it for. A save that names
neither key is not held to the rule.

`typedTokenAtLinkProblem` refuses a stored `ADMIN_API_TOKEN` at the address of
the manager's link while the link stores a token, since the admin there takes
only a token of the deployment's own. Leave the token empty there, and the first
deploy generates one.

## The manager's own link

`manager_admin_link` is a table with exactly one row: the address, or null for no
default, the token, a revision a save names, and who saved it last. The address
is answered in clear. The token column is never selected by a read, only
`token IS NOT NULL`. Two things read it: the stage publisher, which presents it
as the registrar token, and Test connection. The columns refuse a token with no
address, a token under 32 characters and an empty address.

A save names the revision it read, so two operators cannot overwrite each other
unseen. An empty address removes the link and its token with it.

A deployment created while the link has an address and a token starts with the
link's address, and keeps what it was created with in its own settings. A create
never copies the link's token. The link still reaches the deployments that exist,
through their stages: the stage publisher pushes the record of every deployment
whose `ADMIN_API_URL` is on the link's origin to the link's address with the
link's token ([stages.md](stages.md#to-whom)). A new token is used at the next
push. An address on another origin stops their pushes with
`skipped-other-origin`, since each deployment keeps its own address.

## A token of its own

Every uploader linked to the manager's admin presents a token of its own
(`manager/src/domain/adminLink/ownAdminToken.ts`). A deploy generates
`ADMIN_API_TOKEN` for a deployment when all of these hold:

- it runs a stream uploader,
- the address its next deploy gives the uploader is on the origin of the
  manager's link (`sameAdminOrigin`), and the link stores a token, which is what
  registers the deployment's stage, and so the new token, with the admin,
- the deployment stores no `ADMIN_API_TOKEN` of its own, and its version's env
  files set none.

The value is 64 hex characters, like every secret the manager generates. It is
kept in the deployment's `stack_secrets` beside them and written into its env
file. A stored value is never replaced, because the running uploader was started
with it. It is written only while the address stays on the link's origin, so it
never goes to another admin. The stage record carries its sha256 with the kind
`own`, and the push a deploy makes before it starts the uploader registers it, so
the uploader's first call finds it known.

The record's `adminToken.kind` says where the token came from, never whether it
equals the link's. It is `own` only for the token the manager generated for the
deployment (`NextDeployEnv.ownAdminToken`), and `shared` for any other: a typed
token, a copy of the link's, or a version's. The admin refuses every `shared`
token from an uploader. Its Stages page says the token is refused until it is
rotated, and the deployment's Test connection answers `token-not-own`.

### Rotating an uploader's token

**Rotate the uploader's admin token**, on the deployment page's Web2 admin stage
card (`POST /profiles/:name/admin-token/rotate`), moves a deployment to a new
token of its own. `ProfileRepository.clearAdminToken` takes out, in one
statement, the generated token and a token stored in the settings, with the
origin recorded for it and a new settings revision when there was one. The
statement runs only while the deployment is not in the middle of a deploy, stop
or removal, and checks that itself: a deploy that starts after the rotation read
the row makes it answer `profile_busy`, and nothing is taken out.

The deployment's change event makes the stage publisher push at once. The record
then carries no token, so the admin stops taking the old one, and the uploader
cannot report until the redeploy. That deploy generates the new token and
registers it before starting the uploader.

The rotation is refused, with a sentence, where that redeploy would generate
nothing:

- a deployment that runs no stream uploader,
- one in the middle of a deploy, stop or removal,
- one whose uploader is given another address than the link's,
- a link with no token,
- a version whose env files set `ADMIN_API_TOKEN`.

### A token the version sets

A deployment whose version's env files set `ADMIN_API_TOKEN` is given that value
at every deploy, in place of a token of its own. Its record says `shared`, which
the admin refuses, and the rotation is refused for it. Take the token out of the
version, or move the deployment to a version that sets none, and redeploy. The
deploy then generates a token of its own.

## Where a stored token may go

A stored token goes only to the origin of the address it was stored for.
`sameAdminOrigin` in `common/src/adminLink.ts` compares the two as the WHATWG URL
parser normalizes them: the host lowercased, a default port dropped, IPv6 and
IPv4 forms rewritten. A path may change. A host with a trailing dot is another
origin, which refuses more and never less. An address with no origin, empty
included, matches nothing.

- **The manager's link.** A save that moves the address to another origin has to
  come with a new token or a cleared one, or it is refused with a sentence saying
  so. Test connection with the stored token asks nothing at an address on another
  origin and answers `stored-token-elsewhere`, so an unsaved address there needs a
  typed token.
- **A deployment's own token.** `profiles.admin_token_origin` holds the origin its
  stored `ADMIN_API_TOKEN` was stored for. A create that types the token, a save
  that stores or takes out the token, and a member added to a group from its
  siblings write it. An empty string is a token stored with no address, which goes
  to none until it is typed again with one. A save that moves `ADMIN_API_URL` to
  another origin, a reset that puts back the version's address elsewhere
  included, has to come with a new token or a cleared one. A deploy that would
  give the uploader another origin, because the version's own address moved under
  it, is refused with a sentence naming both keys, and the card's Test connection
  answers `stored-token-elsewhere` without asking anything. A stored token with no
  recorded origin is recorded by its next deploy, for the address that deploy
  gives the uploader.

The pages say it before the manager refuses. The Manager settings card names it
under the token field and keeps Save and Test connection off. The wizard's group
says the manager's stored token was saved for another address, holds Continue,
and offers a button that moves to a token typed there, with focus in its field.

## Plain http and the manager's own host

Every push carries the registrar token, each stage's SRT passphrase and its token
hash, so in production the link's address is the https one the edge serves the
admin on. The manager takes plain http only to its own host
(`manager/src/domain/adminLink/plainHttpAdminLink.ts`). Its own host is:

- a loopback address, and `localhost`,
- `host.docker.internal` and the addresses it resolves to, which is the host's
  bridge,
- while the manager runs in its container, any address on a Docker network that
  container is on, such as the admin's compose service name when the two share a
  network. A link-local range never counts.

Every address a name resolves to has to be one of those. So plain http that names
the manager's own machine by its public address, its LAN address or a public name
is refused like any other host. Plain http is safe on a Docker network only when
that network is a bridge, which stays on the machine. An overlay, macvlan or host
network can carry the traffic off it, so a link reached over one of those needs
https.

A name that does not resolve from the manager now is neither taken nor refused.
Docker's own DNS answers no address for a service whose container is not running,
so a link to the admin's service reads that way while the admin is stopped or
redeployed. A save of such a name is taken, a send to it is not made and comes to
`unreachable`, and the next send judges it again once it resolves. The text of an
address cannot tell a service name from another host's name, so
`plainHttpAdminLinkHost` in `common/src/managerAdminLink.ts` only picks out the
host to judge, and the manager judges it by what it resolves to.

A save of plain http to another host is refused with a sentence saying why. Every
send to such an address is not made: a push comes to `refused-plain-http`, and
Test connection with the manager's token to `plain-http-refused`. The card says
nothing while an address is being typed. The manager's
`ADMIN_LINK_ALLOW_PLAIN_HTTP=true` takes plain http to any host, for a test
setup, and a save of one then logs a warning.

Moving a plain http link to https changes the link's origin. A retirement still
pending for the old origin is then dropped, with a log line, and the stage behind
it stays active at the admin. Switch the link once the pending retirements have
gone through. Where `ADMIN_LINK_ALLOW_PLAIN_HTTP` is what lets the link through,
keep it on until then. The log names each retirement as the admin answers it.

## Test connection

`manager/src/domain/adminLink/adminLinkProbe.ts` asks what the holder of the
token would ask.

**The manager's own token**, stored or typed on the Manager settings card, is the
registrar's. It is proved on the admin's registrar check,
`GET <address>/api/internal/registrar` with the bearer token, which answers `204`
(`token-accepted`) or the admin's own 401 (`token-refused`). No owner is compared.
That token goes in plain http only where the manager's pushes may, so an address
in plain http to another host answers `plain-http-refused` and is not asked. An
admin without the registrar check answers its own `404 not_found` there, and only
then is the uploader's lookup below asked with the same token.

**An uploader's token**, a deployment's or one typed in the wizard for another
admin (`tokenFor: 'uploader'` on the request), is proved as the uploader proves
it. First comes the internal lookup of a stream nobody can have declared,
`GET <address>/api/internal/streams/by-ingest/video/00000000-0000-0000-0000-000000000000`,
with the bearer token. The admin checks the token before anything else, so its
own 404 says it took the token and its own 401 that it did not, each told apart
from any other server's by the error code in its body.

A deployment's test presents the deployment's own token, which the admin knows
once the stage was pushed. At the link's address, while the link stores a token:

- a token of the deployment's own that the admin refuses, while no push of its
  stage has been stored, answers `token-not-registered`, since a deploy registers
  it,
- a token the manager did not generate for the deployment answers
  `token-not-own`, whether the admin refused it or took it. Rotate the uploader's
  admin token and redeploy.

At another address a refusal is `token-refused`.

Then, where there is a stream address to compare, the test asks what the uploader
asks at boot. Every stage signs with a key of its own, so the owner compared is
the one the admin knows for the stage the token belongs to:
`GET <address>/api/internal/stages/self` with the same token, whose
`{ stageId, owner }` answers `linked` or `owner-mismatch`. On a 404 there, from an
admin that knows no stages, the admin's public `GET <address>/api/config` is
asked, without the token, for `feed.owner`, the key the catalogue is signed with.
Any other answer to the stage read is `owner-unconfirmed`. Both are compared the
way the uploader compares them, without case and with or without `0x`.

The stream address a deployment's test compares is the address of the
`STREAM_KEY` its next deploy gives the uploader: the deployment's own key or,
where it stores none, the one its version's base `.env` sets. The manager derives
it in memory with `addressOfStreamKey` in `common/src/streamKey.ts`. The key goes
nowhere: not to the admin, an answer, an error or a log line. A deployment for
which neither sets a key compares no owner.

The wizard's test depends on the token choice. With a token of its own, it proves
the manager's stored token on the registrar check and compares no owner, since
the uploader's token does not exist before the first deploy and the admin learns
the stage's address from its first push. The deployment's own Test connection
compares it once the stage exists. A token typed in the wizard is an uploader's,
for another admin than the manager's own. Its test compares the address of the
stream key chosen in the step, which the browser derives with the same function.

The probe takes http and https alone, follows no redirect and says so, gives up
after five seconds a request, the uploader's own lookup timeout, and reads at most
64 KiB of an answer. It never throws. Its answer is one outcome code
(`ADMIN_LINK_TEST_OUTCOMES` in `common/src/adminLinkTest.ts`), never anything the
admin said, the address or a token. The log names who tested and the outcome.

| Outcome                  | What it means                                                                              |
| ------------------------ | ------------------------------------------------------------------------------------------ |
| `linked`                 | the admin took the token and knows the deployment's stream address as its owner            |
| `token-accepted`         | the admin took the token, and there was no owner to compare                                |
| `owner-unconfirmed`      | the admin took the token but did not say which address it signs with                       |
| `owner-mismatch`         | the admin took the token but knows another owner, which the uploader refuses to start with |
| `stored-token-elsewhere` | a stored token was saved for another origin, so nothing was asked                          |
| `token-refused`          | the admin refused the token                                                                |
| `token-not-own`          | a deployment's token at the link's address is not one the manager generated for it         |
| `token-not-registered`   | the admin refused the deployment's own token, and no push of its stage has been stored yet |
| `not-admin`              | something answered, but not as a web2 admin answers                                        |
| `redirected`             | the address answered with a redirect, which the test does not follow                       |
| `unreachable`            | nothing answered from where the manager runs, in time or at all                            |
| `invalid-address`        | the address is not an http or https one the uploader could use                             |
| `plain-http-refused`     | the address is plain http to another host than the manager's own, so nothing was asked     |
| `not-linked`             | there is no address, so the uploader runs standalone                                       |
| `no-token`               | there is an address and no token, which the uploader refuses to start with                 |

### What it reaches

The test runs from where the manager runs, so an address only the deployment's
own network can reach reads as unreachable, and the page says so beside every
Test connection button. It reaches whatever the manager's host can reach,
loopback and private addresses included, as the uploader reaches whatever its
host can. Every route that tests or edits the link needs a session, and a
signed-in user learns an outcome code and nothing else.

## In the console

- **Manager settings**, a page in the navigation. Its admin link card
  (`frontend/src/adminLink/ManagerAdminLinkCard.tsx`) saves the address and the
  token and tests them.
- **The new-deployment wizard's Web2 admin group**, for every goal that runs a
  stream uploader (`frontend/src/forms/wizard/adminLinkChoice.ts` and
  `steps/AdminLinkGroup.tsx`). It follows the manager's link until you touch it,
  and holds Continue while that link is read. Its token choices are:
  - **A token of its own**, generated at the first deploy. Offered only at the
    link's address while the link stores a token.
  - **A token typed here**, for another admin. Held at the link's address while
    the link stores a token, with a sentence and a button back to a token of its
    own.

  Switched off, the create stores an empty `ADMIN_API_URL`. When the link cannot
  be read and you leave the group alone, the group says so with **Try again**,
  and the create sends neither key, so the manager adds its own link. Under
  Advanced settings the two keys point at the group.

- **A deployment's Stack settings card**, where the two keys are ordinary fields,
  with Test connection right after them
  (`frontend/src/deployments/settings/adminLinkRow.ts`). A generated token shows
  there as generated by the manager.
- **A deployment's Web2 admin stage card**, with **Rotate the uploader's admin
  token** (`frontend/src/deployments/StageCard.tsx`).

Every sentence can be seen with `pnpm -C frontend dev:mock`. The mock manager's
Test connection reads its outcome off the address, so
`https://unreachable.admin.offline.example` answers `unreachable`, and so on.

## Settings and routes

| Setting                       | Where          | What it does                                                                                                                          |
| ----------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `ADMIN_API_URL`               | the deployment | the admin the uploader reports to. Empty leaves the uploader standalone                                                               |
| `ADMIN_API_TOKEN`             | the deployment | the token the uploader presents, at least 32 characters. Generated by the manager where it can                                        |
| `ADMIN_LINK_ALLOW_PLAIN_HTTP` | the manager    | `true` takes plain http to any host, for a test setup. Off by default, and any value but `true` or `false` stops the manager at start |

All routes are behind the session, and every write behind the same-site check.
The full reference is
[the API reference](../../manager/README.md#linking-uploaders-to-the-web2-admin).

| Method | Path                                       | Body                                                | Answer                                                       |
| ------ | ------------------------------------------ | --------------------------------------------------- | ------------------------------------------------------------ |
| GET    | `/manager-settings/admin-link`             |                                                     | `{ url, tokenStored, revision }`, never the token            |
| PUT    | `/manager-settings/admin-link`             | `{ expectedRevision, url, token? }`                 | the link after the save. No `token` keeps it, null clears it |
| POST   | `/manager-settings/admin-link/test`        | `{ url, token: { source }, tokenFor?, feedOwner? }` | `{ outcome }`                                                |
| POST   | `/profiles/:name/settings/admin-link/test` |                                                     | `{ outcome }` for what the next deploy gives the uploader    |
| POST   | `/profiles/:name/admin-token/rotate`       |                                                     | `{ message }`, the sentence the card shows                   |

## Limits

- A create through the API is given the manager's link only when the link stores
  an address and a token. An address alone is not given, since the uploader would
  refuse to start with no token.
- A token of its own is written only for the link's origin. A link moved to
  another origin after the deploy that generated it leaves the deployment's
  uploader without it. Such a deployment is refused at save by the rule, and at
  deploy its uploader refuses to start until a token is typed for the address or
  the link is put back.
- A stored token at the link's address is refused at a save and a create. One
  already stored stays until a save of either key or a rotation takes it out, and
  its Test connection says `token-not-own`.
- A token typed for another address reaches only an admin that still takes typed
  tokens from uploaders. An admin that takes only a stage's own token learns it
  only from the manager linked to it.
- The card's test uses the saved values. A change that is not saved yet is tested
  once it is saved, and the card says so while one is pending.
- A signed-in user can save the manager's link with an address and a new token of
  their own, or type a token for any address. The stored token itself goes only to
  the origin it was saved for. The same user can already deploy containers on the
  host.
- The origin rule guards the tokens the manager stores, the manager's and a
  deployment's own. A token the version's base `.env` sets travels with that
  file's own address and is not held to it.
- A query string in the address passes the field and reaches the uploader, which
  puts its paths after the query and so asks the wrong thing. Test connection
  builds its requests the same way and answers `not-admin` for it.
- The page cannot tell an empty token from a stored one before a save, because no
  secret value reaches it. The rule on the two keys is answered by the manager's
  refusal under Save rather than before it.
